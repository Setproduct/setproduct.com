This guide covers button anatomy and the state set every button must handle. It walks through sizing and theming, plus the priority rules for actions. ## TL;DR

- A button triggers an action in place. A link moves you to another page. Keep the two roles apart.
- One primary button per section, everything else is secondary or tertiary.
- WCAG 2.2 sets a 24×24 px minimum target, 44×44 on touch.
- Focus-visible is mandatory, and button text contrast starts at 4.5:1.
- Every button needs the full state set: idle, hover, focus, active, loading, disabled.

## Button vs link vs chip vs icon button

The fastest way to get buttons right is to pick the correct control first. A button and a link look similar but behave differently, and mixing them up is the most common source of broken UI.

| Control | When to use it | When not to use it |
|---|---|---|
| Button | Action in place: submit, save, open a modal | Navigation to another URL |
| Link | Move to a page or an anchor | Trigger an action without navigation |
| Chip | Pick from a set or apply a filter | The main action of a form |
| Icon button | A familiar action with no room for a label | An action that is unclear without a name |

The [chip UI design guide](/blog/chip-ui-design) covers selection patterns, and the [button group guide](/blog/button-group-guide) covers grouped actions.

## Buttons anatomy

States matter because they tell the user what a button is doing right now. Visual cues let people read the purpose and status of a control at a glance, then act.

❶ **Default.** The idle state. Normal appearance, ready to start an action.

❷ **Hover.** Fires when the cursor moves over the button. Usually a different background, to signal the control is interactive.

❸ **Active.** The pressed look while the user interacts with it. The button turns brighter or darker to make the press obvious.

❹ **Focused.** A keyboard or click focus shows a bold outline around the control, so the active element is clear.

❺ **Disabled.** The button is unavailable. A shaded look and no click response.

❻ **Loading.** The button is processing an action, shown with a spinner so the user knows to wait.

Icons inside of buttons can be used to help quickly communicate what action the element will take. They can be used to help users quickly and easily identify what will happen when they click on the button.

## Buttons Theming

### Styles

By using different styles of buttons, UI designers can communicate different messages to in-app users and create an intuitive flow through the user interface. There are four different kinds of buttons that you should know about:  

1.  **Text Only or Link Button**: Is simply text-based, without any visual elements. Use for actions that don't require full attention, such as "Cancel" or "Done".  
      
    
2.  **Contained or Filled Button**: Is typically filled in with a solid color and can hold a text label or an icon. They usually indicate an important action, such as "Submit" or "Save".
      
    
3.  **Outlined or Ghost Button**: is similar to contained BTN, but is outlined with a color or a border. Utilize it to indicate a lower-priority action or a secondary option.  
      
    
4.  **Shaded or Tint Button**: has a half-transparent color overlay. This type is used to indicate a less important action when placed together with Contained Button.

### Corner radius

By varying a radius from **0px** to **99px** you can go from a Square Button up to a Pill Button.

The corner radius of a button in UI design affects the visual appearance of the element, as well as the user's perception of the interface. By varying a radius from _0px_ to _99px_ you can go from _Square Button_ up to _Pill Button:  
_

-   **0px** radius will create a sharp, angular look that is more suitable for an enterprise interface. This will help create a clean, minimal design that is easy to percept.

-   **8px** radius adds a bit of visual interest to the button and allows it to stand out from the other components. Thus, for users it's easier to find and interact with the button.  
    

-   **16px** radius creates a more rounded, organic style that is softer and more welcoming. This is a great option for buttons that are intended for common actions.

-   **99px**\+ radius creates a very rounded, circular look that is often used for buttons that are meant to be eye-catching. Such a Pill button highlights among the other UI bits and encourages users to interact.

## UX & Usability

### Accessibility

A button must work for everyone, including people who navigate by keyboard or use a screen reader. The [WCAG 2.2 guidelines](https://www.w3.org/TR/WCAG22/) set the baseline:

- **Target size (minimum) 2.5.8.** Every button is at least 24×24 CSS px, and 44×44 on touch screens. Small icon buttons need a larger invisible hit area around the visible icon.

- **Focus visible 2.4.7 and 2.4.11.** A keyboard focus ring stays visible on both light and dark backgrounds. Never remove the outline without a replacement.

- **Contrast 1.4.3.** Button label contrast starts at 4.5:1 against the button background.

- **Name, role, value 4.1.2.** Use a real `<button>` element, not a `<div onclick>`. A screen reader then announces the control and its state.

- **Disabled state.** When a button must stay focusable for context, use `aria-disabled` instead of the `disabled` attribute.

## Buttons size

![Panda Dashboard UI kit for Figma](/blog/assets/button-ui-design/img-9.svg)

Variety of buttons by [Panda Dashboards](https://www.setproduct.com/templates/panda)

The size of a button in UI design is important because it affects its usability and summarized user experience. Using different sizes allows designers to emphasize different actions, guide users' attention, and create a better in-app flow.  

-   **Small buttons** are often used to indicate actions that are secondary, as they are less visually prominent and easier to fit in a smaller area.

-   **Medium buttons** are the most commonly used button size. They are a good balance between visibility and space-saving, and are often used for default actions.  
    

-   **Large buttons** to emphasize the importance of an action. They are more visible and eye-catching; great for drawing attention to a key activity.

-   **XL buttons** to draw max attention. They are the most visually prominent and are great for guiding users' sight and focus on what's matter most for a business.

## Buttons priority

Primary and secondary buttons are often used together in app design to provide a visual hierarchy. By implementing such an approach, you help your users to quickly identify and understand which action is most important.**‍**

**Primary buttons** are used to indicate the main action the user should take. They are usually more prominent and colored differently to stand out.**‍**

**Secondary buttons** are used for less important functions, e.g "Cancel" or "Help." Placed together with primary, secondary buttons should be less visible to indicate their lower importance.

By varying background fill and border, primary and secondary buttons help users spot the most valuable action on a page or in an app.

## Anti-patterns

A few patterns look fine in a static mockup and fail in a real product.

- **Icon-only button with no label.** If the icon is not universally known, add a tooltip or a visible label. A screen reader still needs an accessible name.

- **Removing the focus outline.** Killing the outline for aesthetics locks keyboard users out of the control. Replace it with a visible style, do not delete it.

- **Disabled button with no reason.** A greyed-out button that never explains why it is blocked leaves the user stuck. Show the missing field or the required step.

- **Loading state that shifts width.** Swapping the label for a spinner resizes the button and the layout jumps. Reserve the width before the state changes.

- **Too many primary buttons.** Two competing primary buttons on one screen dilute priority. Keep one primary action per section.

## Frequently asked questions

### ❶ What is the difference between a button and a link?

A button triggers an action on the current page, while a link moves the user to another URL or an anchor. The semantics differ: `<button>` versus `<a>`, and that changes keyboard behavior and screen reader output. Pick the element by meaning, not by how it looks.

### ❷ How many buttons should be on one screen?

One primary button per section, with everything else secondary or tertiary. Several competing primary buttons dilute the hierarchy and slow the decision down. When actions multiply, group them or push the extra ones into a menu.

### ❸ What button size is accessible?

WCAG 2.2 sets a 24×24 CSS px minimum, and 44×44 is comfortable on touch screens. Button text needs at least 4.5:1 contrast. Small icon buttons need a larger hit area around the visible icon so the target still passes.

### ❹ Should disabled buttons be used at all?

Less often than most teams do. A blocked button does not explain the cause. It is usually better to keep the button active and show the error on press, or state what is missing next to it. When you must disable it, add a hint that says why.

### ❺ What states must every button have?

Idle, hover, focus, active, loading, disabled. Focus-visible is mandatory for keyboard users, and loading replaces the label with a spinner without shifting the width. A button missing any of these states feels unfinished.

### ❻ How do I handle buttons on mobile?

Raise the target to 44×44, keep the primary action away from the screen edge, and avoid hover-only hints. On narrow screens the primary action often moves into a sticky bar at the bottom, while secondary actions fold into a menu.

## Checklist before you ship

→ One primary button per section, the rest secondary or tertiary
→ Tag chosen by meaning: `<button>` for actions, `<a>` for navigation
→ Full state set present: idle, hover, focus, active, loading, disabled
→ Focus-visible reads on both light and dark backgrounds
→ Target size at least 24×24 px, 44×44 on touch
→ Label contrast at least 4.5:1
→ Label in sentence case, verb first, 1–3 words
→ Loading state does not shift the button width
→ Icon-only buttons carry an `aria-label`
→ A disabled button, if any, explains the reason
